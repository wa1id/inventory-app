Test fixtures for InventoryNetworkTests, generated by running the real TypeScript.
Do not edit them by hand; each generator's header has the commands to regenerate.

| File | Generator | Contents |
| --- | --- | --- |
| `client-vectors.json` | `generator/client-vectors.test.ts` (Jest, `logic` project) | The RN clients run against canned answers: `householdRequest`'s body parsing, error codes and 409 stamps; `listDevices`' lenient entries; `parseRecognitionResponse`; `parseBackupList`; JS `String()`, `Number()`, `Number#toString` and `encodeURIComponent`. Lone surrogates in expected values are written as U+FFFD (`toWellFormed`), how the Swift clients read them |
| `household-contract.json` | `generator/household-contract.mts` (tsx, from `home-server/`) | Every household endpoint the app calls, sent to `home-server/src/app.ts` over a fresh SQLite household exactly as the RN client builds the request, with the server's real answers. Ids and clocks are seeded; tokens and the household code are fixed placeholders. Also an import of a photo row with NULL dimensions, sent with explicit `null`s (accepted) and with the keys left out (refused: the importer binds them straight into SQLite) |
| `sync-contract.json` | `generator/sync-contract.mts` (tsx, from `worker/`) | Every sync Worker call, sent to `worker/src/index.ts` over the in-memory R2 bucket from `worker/test/fakeR2.ts`, with the Worker's real answers and headers |
| `recognition-contract.json` | `generator/recognition-contract.mts` (tsx, from `server/`) | `POST /api/recognize` (`server/api/recognize.ts`) with a scripted vision adapter: each outcome's answer, and what the server handed the adapter (declared media type, cleaned hint) |

The contract tests replay these answers through a real `URLSession` whose
requests a `URLProtocol` stub serves, and check that the Swift clients send the
same method, path, headers and JSON the RN client sent to the real server.
